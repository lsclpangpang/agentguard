## 目标与记录范围

对受管程序已经采集并确认归属的每条允许、阻止访问，逐条保存到本机，支持重启后回查和导出；重复访问也分别保存。界面可以汇总显示次数，存储层不采样、不按路径去重。

记录包括文件读写、程序执行、系统提供的连接目标、Unix 套接字和进程信号拒绝等。只保存事件元数据，不保存文件内容、对话正文、环境变量、认证信息、完整命令参数或网络载荷。

“已记录”有两个必须明确的边界：

1. 记录系统提供、采集器实际收到且可以确认归属的事件。采集遗漏、无法归属和未支持的事件类型都必须明确显示，不能宣传为所有系统调用的完整审计。
2. 历史访问结果来自当时的事件证据。`allowed_observed` 表示采集器观察到访问成功，`denied` 表示系统明确报告拒绝；不以当前权限配置重新推测历史结果，也不把“没有拒绝日志”推断为成功。

## 设计前基线与本期范围

设计前，Helper 每个程序在内存中保留最多 5000 条 Observation，接口返回最近 400 条，界面只渲染其中前 200 条，逐次访问明细没有持久化。原有 decisions.json 和 history.json 保存处理决定及权限、启动停止历史。

设计前，采集器的进程 fork、exec、exit 事件持续订阅，文件事件只随学习模式订阅。因此，只把原有内存数组写入文件，仍然不能满足强制保护模式下成功文件读写也要保存的要求。

第一期正式交付同时包含：

- 独立的访问日志存储与清理。
- 将文件事件订阅条件由“有程序处于学习模式”改为“有程序处于学习模式，或有程序启用访问日志”。沿用现有 file-events 控制路径，不切换受管程序的保护模式，不新增受管程序权限。
- 先由现有进程归属逻辑过滤，再写入对应程序的日志。不持久化整机原始 eslogger 输出。
- 显示实际采集能力：文件事件是否已订阅、采集器是否健康、是否存在进程归属缺口。成功 TCP/UDP 连接目前没有相应采集来源，第一期不承诺记录其全量明细；已有系统拒绝目标仍正常记录。

仅完成存储底座可以作为内部开发阶段，不能作为上述需求已全部交付。

## 默认值

下表的存储、清理与 Helper 参数已随 build 75 安装；Collector 发送队列是后续 build 76 源码修订，尚未替换本机稳定采集器。它们约束各自收到记录的排队或存储容量，不能保证上游系统事件完整送达；实际运行证据及未通过项见验收记录。

| 项目 | 建议 |
| --- | --- |
| 默认范围 | 对受管程序启用；只保存能够确认属于受管程序的事件 |
| 保留期限 | 最近 7 × 24 小时，按完整分段淘汰 |
| 单个程序上限 | 256 MiB |
| 全部访问日志上限 | 512 MiB，包含活动分段、元数据和损坏分段 |
| 单段上限 | 16 MiB，或持续写入 1 小时，先到即轮转 |
| 批量写入 | 不超过 1 秒或 256 条事件，先到即提交 |
| 磁盘同步 | 正常负载下最长每 1 秒同步一次；轮转、正常关闭时同步 |
| Helper 事件队列预算 | Helper 内采集入口与写盘排队共用最多 8 MiB 或 10000 条，先到即视为拥塞 |
| Collector 发送队列预算 | 独立于 Helper 预算；最多 4 个客户端，每客户端最多 2 MiB 整帧数据或 128 帧；另缓存最多一条 1 MiB 编码行及换行的初始状态帧 |
| 定期清理 | 启动时、轮转时、容量不足时，以及每 15 分钟 |
| 查询分页 | 默认 200 条，单次最多 500 条；限制单次扫描和响应大小 |

7 天是目标保留范围，不是最低保留保证。事件量较大时，容量上限会先淘汰旧记录。为了不改写仍含有效事件的分段，按分段最后事件时间判断过期，最旧记录可能额外保留一个分段，通常不超过 1 小时。

## 保存位置和格式

建议位置：

```text
/Library/Application Support/AgentGuard/access-logs/<profileID>/
  <segmentID>.open.jsonl
  <segmentID>.jsonl
  <segmentID>.meta.json
```

沿用现有受保护配置根目录。由 Helper 写入，目录 root 所有、权限 0700，文件 0600；App 通过现有签名校验的通信接口查询和导出。受管程序不获得日志目录的读写权限。

使用追加式 JSONL，每行一个版本化记录，按大小或时间封段。首版不引入数据库、全文搜索、压缩或远端上传。日志可以直接按行检查，清理可以删除完整分段；无需反复重写整个历史数组。

每段有开始记录及封段元数据。元数据包含首末序号、首末接收时间、各类记录数量和字节数，供查询和容量统计使用；它可以从日志重建，不能成为读取真实日志的唯一依据。

SQLite 在复杂全文查询、多条件索引成为实际需求时再评估。本轮选择 JSONL，避免同时引入数据库迁移、WAL 管理和空间回收机制。

## 每条事件的数据

| 字段 | 含义 |
| --- | --- |
| schema_version / record_kind | 格式版本；access、gap、storage_status 等 |
| event_id / writer_id / sequence | 唯一事件、此次写入进程身份及单调序号 |
| received_at | Helper 接收时间，使用 UTC；界面按本地时区显示 |
| source_at | 能可靠解码的系统原始事件时间；未提供或格式不识别时为空，不用接收时间或进程启动时间补造 |
| profile_id / profile_revision | 当时所属程序及运行实例实际使用的权限版本 |
| run_uuid / instance_id / instance_origin | 稳定运行身份、实例编号及创建该编号的 Helper 身份 |
| boot_id / root_process_identity | 系统启动身份、运行实例根进程 PID 及创建身份 |
| pid / pidversion / process_start_time | 系统实际提供的进程身份；缺失项为空 |
| process_name / executable_path | 能从事件可靠获得的程序身份 |
| source / source_sequence | eslogger、sandbox_log 或其他明确来源，及来源序号 |
| operation / target | 读、写、执行、连接、信号等操作及目标 |
| open_flags | 新版记录中系统实际提供的内核打开标志；无有效值时为空，不把缺失当作读取 |
| outcome / evidence | 明确拒绝、观察到成功或无法确认；记录判定依据 |
| raw_target / endpoint_fields | 必要的原始目标与结构化网络字段；未知项为空 |
| coverage / attribution_status | 当时采集覆盖与进程归属状态 |

保留明确来源和原始动作，避免将 create、unlink、rename 全部折叠后失去上下文。当前 Observation 不包含的来源、进程身份及原始动作，需要在事件进入 Helper 时一并传入，不能靠事后按同名进程或复用的 PID 猜测。

运行实例获得独立 run_uuid，写入现有实例记录；Helper 重启后恢复同一实例时沿用它。Helper 会话 ID、系统 boot ID 与进程创建身份分别记录，不能用其中一个代替其他身份。旧实例没有 run_uuid 时在恢复边界生成并标记迁移来源，不声称已经补齐此前身份。

同一底层事件可能产生多条不同路径的访问记录，例如 rename 的来源与目的路径。保留来源事件 ID 和子序号，查询时可识别它们属于同一事件。

重复的系统拒绝报告仍按收到的报告逐条保存，同时保留来源信息；“报告数”不宣称等于真实调用次数。系统未给出域名、URL、端口或信号目标时，明确标记未提供。

## 写入、性能与异常

数据流：

```text
系统事件
  → 采集器实时转发
  → Helper 解析、确认进程归属，冻结来源与进程身份
  → 创建带事件身份的访问记录
  → 能映射为 Observation 的事件另行更新最近访问缓存与建议
  → 有界写入队列
  → 串行追加分段并同步
```

独立串行写入器负责追加、轮转、同步和清理。界面查询使用单独的受限读取任务，避免长查询堵住写入。写盘失败不阻塞受管程序，也不改变权限判定。

扩大文件事件订阅前，同时限制现有采集入口的排队。不能继续为每条事件向 Helper 状态队列无界追加一个异步任务，再仅限制末端磁盘队列。采用共享预算、有界批次和合并唤醒，让审批、取消等控制请求能继续处理；预留空间优先保留进程生命周期与拒绝事件，但不重排保留事件的来源顺序。必须丢弃时明确记录丢失类型；生命周期丢失或无法确定遗漏类型时，将进程归属标为不完整。

采集输入的未完成行另设 1 MiB 上限；超过上限时丢弃到下一个行边界并报告，不能让现有 pending 字节数组无限增长。统计事件队列字节数时包含编码后大小及合理的内存开销，不只计算路径字符串长度。

Collector 每个客户端保有独立 FIFO，由可写通知继续非阻塞发送；已发送的前缀在整条 Data 释放前仍占整帧预算。一次处理最多 256 KiB 或 64 次写调用，空队列挂起通知；临时背压保留偏移，队列满或致命错误仅断开该客户端。生产者同步完成有界入队，不按事件追加异步任务。描述符只在取消回调中关闭，避免旧回调写入或关闭复用后的描述符。Collector 的 8 MiB 是逻辑帧数据上限，与 Helper 的 8 MiB 分开；两者均不是整个进程 RSS 或 eslogger 的内存上限。

`open` 是文件打开通知。只有有效整数内核 `fflag` 明确包含 FREAD/FWRITE 时才形成相应读取或写入建议；模式缺失、非法或没有这两个位时，保存原始打开事件和目标，有效原始标志保存为 `open_flags`，不补造正文读取建议。打开成功不证明随后实际消耗了文件内容。历史旧建议不会因新解析规则自动重分类。

落盘入口必须在现有 Observation 动作映射之前。当前 observe(denial) 会忽略无法映射 access 的拒绝，新设计应在确认受管归属后，先保留来源、原始 operation 和可获得的目标。未知类型作为“系统拒绝，暂未分类”保存，不因无法生成权限建议而丢弃，也不自动生成允许项。同理，成功事件的来源序号及 actor 身份从 onLine/observe 入口取得，不能仅序列化当前缺少这些信息的 Observation。

不承诺“收到事件即已可靠写入磁盘”。界面状态分别报告最近写入时间、最近同步时间、待写数量和写入错误。正常负载下目标同步间隔为 1 秒；突然断电或被强制结束仍可能失去尚未同步的部分。写入拥塞时以实际同步进度显示，不能仍宣称“最多只丢 1 秒”。

处理以下异常：

- **队列拥塞：** 不无限分配内存，不让采集队列等待磁盘。溢出时累计丢失条数、序号区间和起止时间，并为状态记录保留独立的小额内存；恢复后先写 gap，再继续普通事件。
- **磁盘满或只读：** 先执行合法范围内的旧段清理；仍不能写入时显示“日志保存失败”，限频重试。无法落盘的诊断状态也保存在内存并通过系统诊断日志限频报告。
- **采集遗漏：** source_gap 与写盘遗漏分开记录。已有采集序号缺口不能因为日志写入成功就被清除。
- **崩溃退出：** 下次启动检查未封段文件，保留完整有效行，隔离或截去末尾未完成的一行。中间损坏不跳过后宣称完整，需隔离该段并记录原因。
- **无法估计的丢失：** 遇到非正常退出或采集器断开，只说明可能缺失的时段；不能凭空给出精确丢失数量。
- **格式升级：** 新旧段可并存。遇到不支持的版本，保留文件并明确提示，不能当作空日志或自动删除。
- **归属不明：** 不把整机事件分配给 Knodo。记录采集健康及归属缺口摘要，不落盘无关进程的详细行为。

路径、进程名及系统文本全部使用 JSON 编码转义，避免换行、控制字符变成额外日志。单条记录和原始诊断文本设置上限；发生截断时保留截断标记及原始长度，不截断后伪装为完整目标。

## 自动清理

清理仅操作 AccessLogStore 创建并校验的日志分段及其元数据：

1. 先删除已过期的封段。
2. 若单程序或全局容量超限，按最旧封段优先删除，降至对应上限的 80%，减少持续触发清理。
3. 当前写入段到达上限后先封段，再进入淘汰范围；不会边追加边删除同一段。新建段前预留容量，活动段及元数据也计入上限。
4. 磁盘可用空间低于预设保护阈值时，提前清理；仍不足则暂停保存并报告，不继续挤占整个磁盘。建议阈值 1 GiB，实施时核对目标卷可用空间的取得方式。
5. 文件时间异常时不只依赖 mtime 判断。保留事件接收时间、段序号及创建信息；时钟回拨仍由容量限制保证空间有界。

损坏段、恢复产生的隔离文件也计入容量，不允许换个后缀就永久逃避清理。对于未识别文件或路径异常，不跟随、不递归扩散删除，报告人工检查需求；无法释放空间时暂停写入。

目录和文件操作基于已经打开并验证的受保护目录，拒绝符号链接及越界路径；校验 profileID 和文件命名。新建文件、封段重命名及元数据更新采用相应的原子操作和必要目录同步。

清理在专用存储调度下执行，不使用 shell 通配符，不触碰 profiles、backups、decisions.json、history.json 或受管程序数据。查询不能长时间持有旧段文件句柄，避免文件已删除但磁盘空间仍持续占用。

每轮清理仅更新一份摘要：原因、释放字节数、删除段数、剩余最早时间；不为每删一条日志再生成一条日志。首版通过状态接口展示本次 Helper 运行中最近一次清理摘要，不持久化清理历史；Helper 重启后该摘要重新开始。

## 查询、导出和界面

最近访问保留快速内存缓存，历史明细来自日志。重启后可以查询保存的访问；读取历史不会重新生成权限建议，也不会把旧事件当成当前运行实例的活动。

建议界面在“最近的访问记录”中提供：

- 时间范围和“全部／允许／阻止／未确认”筛选，按时间倒序分页。
- 进程、操作、路径或连接目标，以及当时使用的权限版本。
- 日志保存状态、已占空间、最早保留时间、采集或保存缺口。
- 导出所选时间范围，以及清空该程序的访问日志。

实际持久化数据与尚在内存的最近事件按 event_id 合并，避免重复展示；未同步的记录可标记为“保存中”。导出默认只包含已提交的记录，并附采集覆盖、缺口和截断说明。

在现有 App 与 Helper 通信上增加受限请求：

```text
accessLogStatus(profileID?)
queryAccessLog(profileID, timeRange, outcome?, cursor?, limit)
exportAccessLogPage(profileID, timeRange, cursor?, byteLimit)
clearAccessLog(profileID, expectedLogGeneration)
setAccessLogEnabled(profileID, enabled)
```

这些接口继续只对通过现有校验的 App 开放，不扩大普通 CLI 或受管程序的读取权限。查询和导出在调用方指定的 profileID 范围内进行，不接受任意磁盘路径。

游标包含日志代次、分段位置和查询时的上界。清理或手动清空使旧游标失效时，明确返回 history_expired 或 cursor_invalid，不能悄悄从头重查造成遗漏或重复。单次查询有扫描字节预算，预算耗尽返回后续游标及 incomplete 状态，不冒充“没有符合记录”。

导出按小块从 Helper 返回，由 App 写入用户选择的位置，不创建无限增长的后台导出缓存。导出文件由用户管理，不纳入后台日志自动清理。

手动清空通过串行屏障确定截止事件序号，清理截止点之前的磁盘及内存记录，并更新日志代次。截止点之后的新事件继续保存，旧队列中的事件不能在清空后重新出现。清空不会撤销权限或删除处理决定，其行为在现有处理历史中保留一条摘要。自动保留期和容量清理无需每次弹窗。

## 服务边界与升级

建议新增：

- GuardCore：访问日志记录、设置、保留策略、查询与错误模型，可注入时钟和文件存储进行测试。
- GuardHelper：AccessLogStore、串行写入调度、故障状态与受限查询接口。
- AgentGuardApp：状态、分页读取、导出及清空入口。
- GuardCollector/Helper 控制路径：文件事件订阅条件与学习模式解耦，实际订阅状态回报。

实例记录增加可向后读取的 run_uuid。日志记录保留来源身份的可信程度：只有 PID 的拒绝来源不能冒充具备完整 audit-token 身份的事件。

日志设置单独存储，不混入权限修订；启用记录不会新增允许项。App/Helper 的通信能力变化按项目规则升级协议，旧版本明确提示升级，不自动重启正在执行任务的受管程序。

沿用稳定采集器身份是否足够、是否仅需复用现有 file-events flag，由实现时的最小差异核对确定。不得为了日志功能绕过系统授权或替换签名身份。

当前已核对旧稳定 Collector 只有布尔订阅标记，没有受管身份筛选或控制命令入口；保持旧二进制时，下游优化不能省掉 eslogger 全机器 JSON 序列化。原生 Endpoint Security 路线仍需 Apple 批准的客户端 entitlement；本机没有相应签名能力，不能把类型检查、root 或完全磁盘访问当成可运行资格。真正替换 Collector 仍需独立的候选身份核验、来源就绪检查、可中断恢复及回退事务；本轮不把安装文件存在当作运行或授权成功。

Helper 在启动时冻结自身运行签名身份，并将 Collector 的安装决定单独报告。App 和维护入口使用同一判断：通信协议兼容且运行身份与随包已验证身份一致，才显示当前；旧 Helper 没有身份字段时提示更新。只保留了现有 Collector 文件时明确提示需要单独维护，不自动替换或重启受管任务。

历史内存明细不能承诺完整迁移。新增日志从启用时开始保存；之前人工导出的证据继续独立保留，不自动导入冒充连续历史，也不将系统旧日志无归属地批量回填。审计日志不作为可信进程归属表或当前待授权项的恢复来源。

## 实施顺序与验收

1. **持久化核心：** 记录格式、有界写入、轮转、同步、异常恢复及清理。
2. **接入与覆盖：** Helper 归属确认后写入，补齐来源信息；启用独立文件事件订阅，并验证 enforce 仍生效。
3. **可用性：** 重启后查询、分页、状态、导出和清空。
4. **实际验证：** 测量 CPU、内存、写入量和高频事件下的可持续速率，核对建议默认容量；通过后再考虑安装。

验收必须覆盖：

- 受管程序真实允许和拒绝的文件访问、执行与 Unix 套接字拒绝能够逐条保存；缺少来源的事件类型明确提示未覆盖。
- 同路径重复访问、rename 双路径、同 PID 不同版本、不同 Helper 启动周期及不同权限修订不混淆。
- App 重开、Helper 正常重启后历史可查；强制结束后的尾部损坏有明确恢复记录。
- 7 天保留、单程序与全局容量、活动段、损坏段和清理低水位共同作用符合设计。
- 磁盘满、权限错误、队列溢出、时钟回拨、采集器断开及部分历史丢失可见，受管任务不因日志写入阻塞。
- 不能利用符号链接、恶意文件名或路径让清理删除范围外数据；受管程序不能改写或清除日志。
- 查询/导出有界，游标跨清理可解释，历史访问不会重新成为待授权项。
- 记录中无对话正文、认证信息、环境变量及文件内容；未知信息不补造。
